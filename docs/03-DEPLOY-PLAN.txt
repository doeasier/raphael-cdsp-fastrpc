【0】v1 的三处错误（全部为【事实】，证据在 logs/firmware/）
  错误 1 —— 「设备 PIL 是单个 cdsp.mbn 3.4MB」
    【实测】设备是 split 形态：/lib/firmware/qcom/sm8150/Xiaomi/raphael/
       cdsp.mdt 7580 B + cdsp.b00/b01/b02/b03/b04/b05/b06/b08/b10（无 b07/b09/b11）
       + cdspr.jsn 403 B。目录中**没有 cdsp.mbn**。
    证据：
       logs/firmware/readonly-audit.txt  §pil-dir
       内核日志 `Booting fw image qcom/sm8150/Xiaomi/raphael/cdsp.mdt, size 7580`
       DT 属性 firmware-name = "qcom/sm8150/Xiaomi/raphael/cdsp.mdt"
         （logs/firmware/readonly-boot.txt §firmware-name，节点 remoteproc@8300000）
    → 修正：按 split 形态替换 mdt + 9 个 bXX（小写同名），**不要放 cdsp.mbn**。

  错误 2 —— 「基准 deb = 设备当前同版」
    【实测】只对用户态成立，对 PIL 不成立：
       · /usr/share/qcom/dsp/cdsp/ 的 21 个文件 sha256 与基准 deb 逐字节一致
         （fastrpc_shell_unsigned_3 = 1d03f6ca…，build id 357350.2_20201211_224311）
       · 但设备 cdsp.mdt 前 436 B sha = b33f71db…，与基准 deb cdsp.mbn 前 436 B
         （= e569f87d…）**不同**；设备 cdsp.b05 内
         QC_IMAGE_VERSION_STRING = `CDSP.HT.2.0.1-00131-SM8150-1`
       · ELF32 phdr 逐项对比（logs/firmware/readonly-audit2.txt）：
           设备 mdt : b02=227348  b05=2710852  p_offset 末段 0x33a000
           基准 mbn : b02=228148  b05=2735588  p_offset 末段 0x340000（与 2021 新包完全相同）
           前 436 B：设备 b33f71db… / 基准=新包 e569f87d…
    → 【结论】设备当前是「00131 分支 PIL + 2020-12 shell」的**不配套组合**。
      这恰好印证 §16.4 引用的 Radxa / Dmitry Baryshkov 结论
      「libraries / shell must match exactly the DSP firmware」。
      换整套 2021-07-30（PIL 00171 + shell 419065.1 + 全部 skel 同 build）
      同时修掉「不配套」与「版本过老」两个变量，**方向比 v1 更站得住**。

  错误 3 —— 「替换前在 rEFInd 里保留/新增一个已知良好回滚启动项」
    【实测】ESP = /dev/sda30（LABEL="efi"，1G vfat，当前**未挂载**）。
       只读挂载后内容仅 /EFI/BOOT/BOOTAA64.EFI + refind.conf(36644 B，默认样例，
       menuentry 全是注释示例) + drivers_aa64/ + vars/。
       **没有任何 vmlinuz / initrd / .dtb / 第二启动项 / 第二内核**。
       efibootmgr -v 只有 6 个 `scsi N` auto_created_boot_option，无 rEFInd 菜单项。
       SecureBoot efivar = 0（关闭），SetupMode = 1。
    证据：logs/firmware/readonly-boot.txt、logs/firmware/readonly-esp.txt
    → 修正：**不能依赖 rEFInd 回滚**。改为【文件级回滚】：
       备份原 pil/ 与 dsp/ 全部目标文件 → tar.gz → SHA256SUMS →
       一旦失败，用 SSH 把备份原样写回并 systemctl reboot。
       依据：cdsp remoteproc 加载失败不会阻止 multi-user.target（stage2 DTB
       只留 cdsp，其它 remoteproc 已 disabled；q6v5_pas probe 失败只影响 cDSP），
       Ubuntu 本身仍可正常启动 → 文件级回滚路径始终可达。
       ⚠️ 仍需用户保留物理重启 / TWRP 兜底能力（历史上 sshd logind 曾卡死，
          需要物理重启才能恢复 SSH）。

【1】设备侧目标路径（已实测确认）
  A. PIL（10 个文件，split 形态）
     /lib/firmware/qcom/sm8150/Xiaomi/raphael/
        cdsp.mdt   <- raphael-20210730/pil/CDSP.MDT
        cdsp.b00..b06 / b08 / b10 <- raphael-20210730/pil/CDSP.Bxx（小写）
        cdspr.jsn  <- raphael-20210730/pil/CDSPR.JSN（逐字节相同，可跳过）
     【事实】/lib -> usr/lib（usrmerge 软链）；DT firmware-name 明确指向 cdsp.mdt。
     【事实】新 CDSP.MDT 的 12 个 phdr 中 9 个非零 filesz 与 9 个 Bxx 长度逐项相等
            （pack_firmware.py 已断言通过），qcom_mdt_load 可正确加载。
  B. DSP 库（21 个文件）
     /usr/share/qcom/dsp/cdsp/   <- raphael-20210730/dsp/cdsp/*
     【事实】cdsprpcd 的 Environment:
        ADSP_LIBRARY_PATH = /usr/lib/rfsa/adsp;/usr/share/qcom/dsp/cdsp;/data/local/tmp/hvx
        DSP_LIBRARY_PATH  = 同上
        /usr/lib/rfsa/adsp/ 下 21 个条目**全是符号链接**指向 /usr/share/qcom/dsp/cdsp/，
        所以只替换后者即可，链接自动生效；/usr/lib/dsp/cdsp/ 不存在，绝不写入。
     【注意】/usr/share/qcom/dsp/cdsp/libhvx_add_skel.so（自编 7160 B）**不在
        21 文件清单内，必须保留不动**；/usr/lib/rfsa/adsp/ 下对应链接指向
        /data/local/tmp/hvx/libhvx_add_skel.so，也不要动。

【4】执行顺序
  1) 主机侧（✅ 已完成）：离线提取、逐项基准比对、ELF phdr 校验、按 split 形态打包。
  2) 上传（分片，每片独立连接）：deploy-bundle.tar.gz → /root/cdsp-20210730-staging/
     建议 1 MB/片，共 6 片；每片 SFTP 后立刻 sha256 校验；全部收齐后
     `cat part* > deploy-bundle.tar.gz` 并比对整体 sha256。
  3) 设备上解包到 /root/cdsp-20210730-staging/pil/ 与 dsp/，按 deploy-manifest.txt
     逐文件 sha256 比对；任一不符 → 立即中止，设备保持 0 改动。
  4) 只读复核基线：remoteproc0 state=running、cdsprpcd active、/dev/fastrpc-cdsp 在位、
     DTB stage2 仍在（/proc/cmdline 的 dtb= 参数）、Secure Boot disabled。
  5) 备份（见【3】），确认 SHA256SUMS 齐全、tar.gz 可解、rollback.sh 可执行。
  6) 整套替换：先 pil/ 后 dsp/，**32 个文件一次到位，不留混搭**；
     保持原属主 root:root 与权限（pil 原为 0755，dsp 原为 0644）。
  7) 设备上复核新文件 sha256 与 deploy-manifest.txt 全部一致；
     确认 libhvx_add_skel.so 仍在且 sha 未变。
  8) systemctl reboot（**绝不 kexec**）。
  9) 重启后验收（见【5】）。

【5】验收与停止条件
  只读检查：
    dmesg | grep -iE 'cdsp|pas|mdt|remoteproc|auth|scm|firmware'
    cat /sys/class/remoteproc/remoteproc0/state
    ls -l /dev/fastrpc-cdsp*
    grep -a -o -E '[0-9]{6,}\.[0-9]+_[0-9]{8}_[0-9]{6}' /usr/share/qcom/dsp/cdsp/fastrpc_shell_unsigned_3
  判定：
    a) qcom_q6v5_pas / qcom_mdt_load / qcom_scm_pas_auth_and_reset 返回 -22 /
       "authentication"/"verify"/"rollback"/"failed to load" → **PAS 验签或
       anti-rollback 拒绝，立即停止换固件路线**，走【3】回滚，记录为 V51 负结果。
    b) remoteproc0 非 running 或 /dev/fastrpc-cdsp 打不开 → 固件未加载成功，回滚。
    c) cdsp running 但 INIT_CREATE 仍 0x80000453 → **「固件版本过旧/不配套」假设
       不成立或不是唯一原因**，停止换固件路线（不要继续换别的固件版本），
       回到 D8 其它假设（内核 fastrpc 对 unsigned shell 的处理、DSP 侧 ASID 能力）。
    d) 出现 0x80000600 → 优先怀疑版本串分叉，核对 21 个 dsp 文件与 10 个 pil 文件
       是否全部换成同一套，必要时整体回滚。
    e) 成功信号：remoteproc0=running、shell build id 变为 419065.1_20210730_070147、
       `host_main` 打印 `host: PASS`（或至少 INIT_CREATE 不再 BADASID）。
  功能验证命令（沿用现有资产）：
    cd /data/local/tmp/hvx && LD_LIBRARY_PATH=/usr/local/lib \
      DSP_LIBRARY_PATH='/usr/lib/rfsa/adsp;/usr/share/qcom/dsp/cdsp;/data/local/tmp/hvx' \
      ./host_main
    fastrpc_test -d 3 -U 1

【6】风险登记
  · PAS 验签 / anti-rollback：中低。换入的是**同机型官方 China Stable** 固件，
    签名链与原厂 OTA 一致；设备当前 PIL 是更老的 00131 分支，方向为升级，
    anti-rollback 通常只拦降级。但【推测】TZ 可能校验 OEM_IMAGE_UUID 或
    PIL 分支编号，无法在主机侧预验证，只能靠 reboot 后 dmesg 判定。
  · 无 rEFInd 回滚项：已用文件级回滚替代；残留风险是极端情况下 SSH 不可达
    （如 sshd logind 再次卡死）→ 需物理重启 / TWRP。
  · 不刷分区、不改 DTB、不换内核、不装 drop-in、不动 libhvx_add_skel.so。
  · 所有替换均为根文件系统中的普通文件，reboot 后生效，文件级可逆。
